## Project

Unity 3D labyrinth runner game (personal hobby project). Build target includes WebGL (deployed at `https://peli.pomeranssi.fi/labyrunner/`) and Android (`.keystore` present, builds emit `.apk`/`.aab`).

- Unity editor version: `6000.4.6f1` (see `ProjectSettings/ProjectVersion.txt`). Open the project through Unity Hub at this version.
- Solution file: `labyrunner.slnx` referencing the Unity-generated `Assembly-CSharp.csproj` (game scripts) and `Assembly-CSharp-Editor.csproj` (editor scripts). The `.csproj`/`.sln` files are auto-generated by Unity and gitignored — do not hand-edit.
- C# scripts live under `Assets/Scripts/`. Scenes: `Assets/Scenes/Intro.unity` and `Assets/Scenes/Game.unity`. Input bindings: `Assets/GameInputActions.inputactions` (generated wrapper in `GameInputActions.cs`).

## Build / run

There is no CLI build script. All build, play, and test actions go through the Unity Editor:

- Play / iterate: open the project in Unity Editor, press Play on `Assets/Scenes/Intro.unity`.
- Build: `File > Build Settings` → target platform (WebGL for web release, Android for mobile). The Android keystore file `labyrunner.keystore` lives at repo root and is gitignored.
- There is no test framework wired up — no unit tests, no test runner config.

## Architecture

The game is a single-player 3D maze runner. Each level is procedurally generated.

### Procedural labyrinth generation

`Assets/Scripts/LabyrinthCreator.cs` generates the maze with a **randomized union-find / Kruskal-style algorithm**:
- All interior walls start present (`Labyrinth.createWallsInside`).
- All wall indices are Fisher-Yates shuffled, then walked. For each wall, if the two rooms it separates are in different connected components (tracked via union-find with path compression in `findRoot` / `shortenPath`), the wall is removed and the components merged.
- This guarantees a spanning tree of rooms — exactly one path between any two cells, no loops.

The `Labyrinth` class (`Assets/Scripts/Labyrinth.cs`) owns the wall grid. Walls are stored only as SOUTH/WEST per cell to avoid duplication; `hasWallTo`/`setWallTo` normalize NORTH→SOUTH and EAST→WEST by shifting coordinates. Cells outside the labyrinth range return `false` from `hasWallTo`.

`Direction` and `Corner` enums plus `Coordinates`/`CoordinatesWithDirection` structs live in `Assets/Scripts/Coordinates.cs`. Wall encoding for the creator: `wall_index = cell_index * 2 + (0 for SOUTH, 1 for WEST)`.

### Level construction

`CreateLevel.cs` (attached to a `Level` GameObject in `Game.unity`) is the per-level orchestrator:
- Holds prefab references for wall, floor, floorCollider, ending area, ghost, gem, chest, health potion, candle holder, carpet.
- On `Start()` it scales labyrinth size by static `level` counter (`labyrinthWidth += (level-1)*2`, height `+= level-1`), tweaks spawn probabilities (more ghosts, fewer potions per level), instantiates the labyrinth, walls, floor, ending area, then randomly places items and decorations cell-by-cell.
- Coordinate conversion: `toGamePosition(x,y,yOffset)` / `toLabyrinthPosition(Vector3)` — world units = `wallWidth * cell`, plus a `levelOffset` to leave entry space.
- `NextLevel()` increments `level`, persists player health into `healthAtStart`, persists god mode, and reloads scene `"Game"`. `OnNewGame()` resets `level=1`, resets score, reloads.
- God mode: triggered via the `GodMode` input action map (`NextLevel` action) — only acts when `godMode==true`.

### Player

`PlayerControl.cs` uses Unity's new Input System (`GameInputActions`, generated from `.inputactions`). Action maps: `Gameplay` (move/run/jump/attack/teleport/placePortal/quit) and `GodMode` (nextLevel). Movement combines keyboard/gamepad input with an on-screen `FixedJoystick` (touch). The player is a `CharacterController` + `Animator`; movement is smoothed (Lerp on direction and speed) in `FixedUpdate`. `PlayerControl.GetPlayer()` exposes a static reference used across scripts (score/health lookups, ghost targeting).

`PlayerHealth.cs` and `PlayerScore.cs` are per-player components looked up via `PlayerControl.GetPlayer().GetComponent<...>()`. Game over (health → 0) routes through `GameOverHandler.OnGameOver(level, score)` which activates the game-over UI.

### Ghosts

Ghosts (`GhostMover.cs`) move grid cell by cell. Each ghost picks one of three `MoveStrategy` implementations at spawn (random in `createMoveStrategy`): `TurnRightStrategy` (wall-follower), `TurnLeftStrategy`, `RandomTurnStrategy`. Strategy is queried at each cell boundary; the ghost interpolates by `speed * fixedDeltaTime` between cells. `GhostFollower.cs`, `GhostHit.cs`, `AttractToPlayer.cs` handle aggro/collision/pickup-attraction behaviors.

### Teleport / portal

`TeleportEffect.cs` is a singleton-style script using two `static bool` flags (`settingUp`, `teleporting`) toggled by `PlayerControl`. Hold the portal-place input for `setupEffectTime` seconds to stamp `teleportTarget` at current position. Holding teleport fades the player out via a shader `_cutoff` property, then teleports by toggling `CharacterController.enabled` around a `transform.position` write (required — `CharacterController` blocks direct position writes otherwise).

### Wall/coordinate convention to remember

- Cell `(0,0)` is at world `levelOffset + (0,0,0)`. Cells extend in +X (east) and +Z (north).
- `Direction.SOUTH = 0, WEST = 1, NORTH = 2, EAST = 3`. The `directionVectors` array in `CreateLevel` and `moveVectors` in `GhostMover` are indexed by this enum — they must stay aligned with it.
- Wall storage is half-grid: only south and west of each cell. North/east queries get redirected to the neighbor's south/west.

## Code style (observed)

- 2-space indentation, K&R-ish brace style, `camelCase` private fields, no `private` keyword on fields where C# defaults to private. Public Unity-serialized fields use `camelCase` (not PascalCase) — this is the project's convention.
- Heavy reliance on Unity `MonoBehaviour` lifecycle (`Awake`/`Start`/`OnEnable`/`OnDisable`/`Update`/`FixedUpdate`). Physics-affecting movement lives in `FixedUpdate`; input callbacks toggle state read in those updates.
- Cross-script state is sometimes held in `static` fields (e.g., `CreateLevel.level`, `TeleportEffect.teleporting`, `PlayerControl._playerRef`) — these persist across scene reloads, which is intentional.
